# Bridge 性能优化记录

## 改动与资源语义

本轮以 `33c4a581` 为基线，先采集原有往返基准的 CPU、内存 profile，再实施以下三项优化：

- `internal/bridge.CopyBuffer` 使用现有 `buffer.BytesPool`，只复用不超过 64 KiB 的缓冲。较大消息按需分配，不放入该池。连续数据直接复制，分段数据通过 `VisitBytes` 写入独立目标；仍消费一个输入引用，每个消费者保有独立字节和可移动视图。
- `core/endpoint.Endpoint` 在构造时缓存 URL 的标准字符串表示。Endpoint 的字段不可从包外修改，现有 API 没有修改方法，因此重复路由不必重新拼接字符串；协议、地址、查询参数和 Bridge token 均保留。
- `Endpoint.enqueue` 在队列可立即接纳时直接提交，只有等待容量时才创建写超时 Context。调用总超时、调用方取消、满队列错误映射，以及关闭时释放队列、等待 worker 的机制继续适用。

复制池限制的是单块大小，池总保留量仍受并发和 Go GC 影响。队列依旧是四个固定分片，容量按消息条数计算；64 KiB 不是消息大小上限，也不是全局队列内存预算。

已接纳的 ACK 调用超时后，执行器继续拥有复制缓冲，直到 Provider 完成或停服丢弃时释放。不能在调用方停止等待时提前归还池。新增回归覆盖这一场景，以及空消息、分段与滑动视图、池大小边界、超大消息、超时优先级和同分片执行顺序。

## 测量方式

2026-10-22，Windows amd64、Go 1.27.1、Intel Core i5-13400F，基准默认 GOMAXPROCS 为 16。基线使用原提交的完整 `git archive`，仅复制相同的新基准文件；基线和优化版本的测试进程串行运行，不与构建或其他压测并行。未固定 CPU 频率或隔离宿主机其他进程。

微基准覆盖 ACK/oneway、写超时为 0/1s、串行/并行提交，以及不同大小的缓冲复制；每项 500ms、重复三次。oneway 提交结束后，通过每个分片的屏障确认先前任务已消费，避免只测入队而留下未完成工作。

端到端基准通过真实 TCP 客户端、Gate、Node Router 和回包链路，双方采用相同的内存 Registry/Locator。覆盖 64B、256B、1KiB、16KiB 和 1、8、32 个连接，共 24 组，每组 300ms、重复三次。每个连接由一个协程串行收发，最多一个在途请求；连接建立、发现和预热不计时。16KiB 场景仅在测试生命周期内调整全局 Packer 容量，组件销毁后恢复，测试不能并行运行。

多连接结果中的 `ns/op` 表示完成总请求数对应的平均墙钟时间，是总吞吐的倒数，不是单请求延迟。为了核对不稳定的耗时结果，又使用固定测试二进制，按“基线、优化、优化、基线”交替测量 256B、1/8/32 连接，每阶段每组 1s、重复三次，共得到每个版本每组六个样本。

完整基准结果行见 [bridge-optimization-benchmark.txt](bridge-optimization-benchmark.txt)。该文件过滤了组件启动、关闭日志，保留基准名及原始测量数值。诊断用 CPU、heap、block、mutex profile 存在仓库外临时目录，不加入源码。

## 分配结果

下表使用第一轮三次端到端测量中，按 `ns/op` 排序的中间样本；数据包括客户端和服务端的全部分配，不只计算 Bridge。

| 本地路径，单连接 | 基线 B/op | 优化后 B/op | 基线 allocs/op | 优化后 allocs/op |
| --- | --- | --- | --- | --- |
| 64B | 1550 | 961 | 33 | 25 |
| 256B | 2170 | 1169 | 33 | 25 |
| 1KiB | 4784 | 2050 | 33 | 25 |
| 16KiB | 58245 | 20656 | 33 | 25 |

256B 往返减少约 46% 的分配字节、约 24% 的分配次数。交替复测中相同路径的分配次数仍为 33→25，字节数约为 2.18KB→1.17KB。Endpoint 缓存也减少 DRPC 路径的字符串分配；网络批量写等因素使并发场景的分配数不完全固定。

| 微基准 | 基线分配 | 优化后分配 |
| --- | --- | --- |
| 256B 连续 Buffer 复制，输入已创建 | 376 B/op，4 allocs/op | 0 B/op，0 allocs/op |
| oneway，写超时 1s，串行，队列通常有空位 | 384 B/op，5 allocs/op | 0 B/op，0 allocs/op |
| ACK，写超时 1s，串行，队列通常有空位 | 1167 B/op，13 allocs/op | 528 B/op，7 allocs/op |
| Endpoint.String | 80 B/op，1 alloc/op | 0 B/op，0 allocs/op |

池的零分配结果是当前微基准的均摊值，不保证首次调用、GC 后或任意并发负载下均无分配。队列满时仍创建等待所需的超时对象；默认写超时为 0，原有 oneway 提交本身已经没有均摊分配。

## 耗时结论与后续方向

交替复测的 256B 本地路径如下，范围为六次测量的最小值到最大值，括号内为中位数，单位为 μs/op：

| 连接数 | 基线 | 优化后 |
| --- | --- | --- |
| 1 | 44.962–81.820（51.886） | 47.914–94.829（68.467） |
| 8 | 11.030–25.335（18.282） | 10.556–24.162（17.320） |
| 32 | 7.133–27.121（17.085） | 6.348–28.326（16.422） |

区间明显重叠，单连接中位数还出现上升；本轮只确认分配减少，不能宣称稳定的延迟或吞吐提升。原先基准中的 Windows P50=0 现象也仍限制尾延迟解释。

优化前后 CPU 采样都较多落在 Windows 系统调用和网络轮询路径。并行提交的 block/mutex 采样包含 Channel、runtime 内部锁、空闲 worker 和基准框架等待，不能将这些汇总值直接当成业务排队时间或 Endpoint 锁竞争。因此本轮保持现有执行器分片与容量。

下一轮应在实际 Linux container 中固定 CPU 配额，增加独立到达率和慢 Provider 场景，测量队列等待、错误率、CPU、GC 和可信的 P99。达到饱和点后，再根据 profile 决定是否调整分片、容量或业务模型。此次没有更改 Registry/Locator 的锁结构。

## 重现与验证

根模块微基准：

```powershell
go test -p=1 ./internal/bridge ./core/endpoint -run '^$' -bench . -benchmem -benchtime=500ms -count=3
```

在 `network/tcp` 模块运行端到端基准：

```powershell
go test -run '^$' -bench '^BenchmarkBridgeLoad$' -benchmem -benchtime=300ms -count=3
```

验证已执行：根模块 `go build ./...`、`go test ./... -timeout 120s`；受影响包定向 vet、通信与组件相关包三轮 race；TCP 模块构建、vet 和三轮串行/8 连接并发往返 race，覆盖 1KiB 与 16KiB。

根模块 `go vet -stdmethods=false ./...` 通过。完整 vet 的既有 `ReadRune` 签名告警继续保留，没有修改该无关 API。KCP/WS/QUIC、gRPC/RPCX、四种外部 Registry 和 Redis Locator 的独立模块构建、测试编译（`go test -run '^$' ./...`）、vet 均通过。未运行长期手工 TCP 服务器测试或需要外部服务的插件集成测试。
